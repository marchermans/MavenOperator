# Replica Control & Topology Spread Constraint Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Allow users to control the replica count and topology spread constraints of MavenRepository deployments via the CRD spec, with sensible defaults (replicas: 1, topologyKey: kubernetes.io/hostname).

**Architecture:** Add two optional properties to `MavenRepositorySpec` (`Replicas` and `TopologySpreadConstraint`), modify all three reconcilers to read them and pass to `EnsureDeploymentAsync`, and extend `KubernetesResourceManager.EnsureDeploymentAsync` to inject `TopologySpreadConstraint` into the pod template spec. The CRD YAML is auto-regenerated by KubeOps from the spec class, so no manual YAML editing is needed.

**Tech Stack:** C# (.NET 10), Kubernetes client (k8s.Models via KubeOps 13.3.3), KubeOps reconciliation framework, Helm charts.

**Spec:** `.agent/plan/replica-control/plan.md` (this document)

## Global Constraints

- Replicas defaults to 1 when not specified (backward compatible).
- TopologySpreadConstraint defaults to `topologyKey: kubernetes.io/hostname`, `maxSkew: 1`, `whenUnsatisfiable: ScheduleAnyway` when configured but no topologyKey is provided.
- TopologySpreadConstraint is only added when explicitly configured by the user (opt-in, not forced).
- All three reconcilers (Hosted, Proxy, Virtual) must be updated identically for the replicas/topology fields.
- CRD YAML is auto-generated by KubeOps.Transpiler from the C# spec — no manual YAML editing.
- Helm chart `charts/maven-operator/templates/deployment.yaml` contains the operator's own deployment (not the repo deployments) — it does NOT need changes for replica control of managed repos (it already has a configurable replicas field).
- Integration tests must verify both the replica count and TopologySpreadConstraint appear in the created Deployment.

## Review Focus

1. **Replica count drift:** A user sets `replicas: 3` but the deployment shows 1 — the reconciler reads from the wrong property.
2. **Topology key override ignored:** User sets a custom `topologyKey` (e.g. `topology.kubernetes.io/zone`) but all pods land on the same hostname.
3. **Backward compatibility:** Existing repos without `replicas` or `topologySpreadConstraint` continue to deploy with 1 replica and no constraint.
4. **Scale down edge case:** Reducing replicas to 0 should be allowed (replicas: 0 means "scaled down / paused").
5. **Topology mismatch with selector:** If TopologySpreadConstraint's labelSelector doesn't match the deployment's pods, the constraint is silently ignored by the API server — operator should log a warning.

/// <summary>
/// Configuration for a Kubernetes TopologySpreadConstraint applied to repository deployments.
/// </summary>
public sealed class TopologySpreadConstraintConfig
{
    /// <summary>
    /// The label key that defines the topology domain (e.g. kubernetes.io/hostname, kubernetes.io/os).
    /// Defaults to kubernetes.io/hostname when omitted.
    /// </summary>
    public string? TopologyKey { get; set; }

    /// <summary>
    /// How many pods may differ from the minimum number of pods in any topology relative to maxSkew.
    /// Defaults to 1 when omitted.
    /// </summary>
    public int MaxSkew { get; set; } = 1;

    /// <summary>
    /// What to do if a pod cannot be placed to satisfy the constraint.
    /// Defaults to ScheduleAnyway when omitted.
    /// </summary>
    public TopologySpreadConstraintPolicy WhenUnsatisfiable { get; set; }

    /// <summary>
    /// Optional label selector to restrict which pods are counted in the skew calculation.
    /// When null, all pods in the deployment are counted.
    /// </summary>
    public V1LabelSelector? LabelSelector { get; set; }
}

/// <summary>
/// Policy for what to do when a TopologySpreadConstraint cannot be satisfied.
/// </summary>
public enum TopologySpreadConstraintPolicy
{
    /// <summary>Always schedule the pod, even if the constraint is not met.</summary>
    ScheduleAnyway,

    /// <summary>Do not schedule the pod if the constraint cannot be met.</summary>
    DoNotSchedule,
}
```

// Inject TopologySpreadConstraint if configured
if (topologySpreadConstraint is not null)
{
    var constraint = new V1PodTopologySpreadConstraint
    {
        TopologyKey = topologySpreadConstraint.TopologyKey ?? "kubernetes.io/hostname",
        MaxSkew = topologySpreadConstraint.MaxSkew,
        WhenUnsatisfiable = topologySpreadConstraint.WhenUnsatisfiable switch
        {
            TopologySpreadConstraintPolicy.ScheduleAnyway => "ScheduleAnyway",
            TopologySpreadConstraintPolicy.DoNotSchedule => "DoNotSchedule",
            _ => "ScheduleAnyway",
        },
        LabelSelector = topologySpreadConstraint.LabelSelector,
    };

    // Append (don't replace) — there may be existing constraints from other sources
    existing.Spec!.Template!.Spec!.TopologySpreadConstraints
        ??= new List<V1PodTopologySpreadConstraint>();
    existing.Spec.Template.Spec.TopologySpreadConstraints.Add(constraint);
}
```

- The operator's own Helm deployment (`charts/maven-operator/templates/deployment.yaml`) already has a configurable `replicaCount` value — this is separate from the repo deployment replicas and does NOT need changes.
- The `WhenUnsatisfiable` field on `V1PodTopologySpreadConstraint` is a `string?` (not an enum) in the k8s client library, mapping to `"ScheduleAnyway"` or `"DoNotSchedule"`.
